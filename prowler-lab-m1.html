Module 1

Configuration Monitoring

Make sure every change in your account is recorded, so that any later finding can be traced. Use case 4: Configuration Monitoring.

Use case: 4. Configuration MonitoringServices: CloudTrail, AWS Config, S3Time: about 60 minutesCost: very low

Limits of what Prowler checks in this module

  • Prowler checks that CloudTrail and AWS Config are turned on and set up correctly. It does not read the log contents or warn you about a specific change.
  • Requirements to review logs regularly (CIS, PCI-DSS, SOC 2, HIPAA) depend on people and processes, which Prowler cannot check.
  • How long logs must be kept depends on each framework and your own policy. Prowler only checks the settings it can see.
  • The scans in this course cover only ap-south-1. A full account review must scan every region.

What configuration monitoring means

Configuration monitoring means keeping a record of every change made in your AWS account: who did what, when, and what a resource looked like before and after. Two AWS services do this:

ServiceWhat it records
AWS CloudTrailEvery API call: who made it, from where, when, and whether it succeeded. A trail saves these events as files in an S3 bucket.
AWS ConfigThe settings of each resource over time, so you can see how a resource changed. A configuration recorder records the settings.

This module comes first because the other modules depend on it. AWS Security Hub (Module 2) needs AWS Config to run its own checks, and every investigation of a finding starts with the logs.

Cost: CloudTrail's first copy of management events is free. AWS Config charges a small amount for each configuration item it records; for this small project the cost stays very low. S3 storage for the log files costs almost nothing.

Step 1: Build the weak setup (before state)

The build script creates a bucket for log files and a trail with two weak settings. It does not set up AWS Config or access logging.

build/m1-build.sh
#!/usr/bin/env bash
# Module 1 build: logging with weak settings (before state)
set -euo pipefail
cd "$(dirname "$0")/.."
source ./env.sh

TRAIL="$PROJECT-trail"
TRAIL_ARN="arn:aws:cloudtrail:$AWS_REGION:$ACCOUNT_ID:trail/$TRAIL"

# 1. Bucket for CloudTrail and AWS Config log files
aws s3api create-bucket "${A[@]}" --bucket "$LOG_BUCKET" \
  --create-bucket-configuration LocationConstraint="$AWS_REGION"
aws s3api put-public-access-block "${A[@]}" --bucket "$LOG_BUCKET" \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

# Bucket policy: lets CloudTrail and AWS Config write their log files
cat > policies/log-bucket-policy.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "CloudTrailAclCheck", "Effect": "Allow",
     "Principal": {"Service": "cloudtrail.amazonaws.com"},
     "Action": "s3:GetBucketAcl", "Resource": "arn:aws:s3:::$LOG_BUCKET",
     "Condition": {"StringEquals": {"aws:SourceArn": "$TRAIL_ARN"}}},
    {"Sid": "CloudTrailWrite", "Effect": "Allow",
     "Principal": {"Service": "cloudtrail.amazonaws.com"},
     "Action": "s3:PutObject", "Resource": "arn:aws:s3:::$LOG_BUCKET/AWSLogs/$ACCOUNT_ID/*",
     "Condition": {"StringEquals": {"s3:x-amz-acl": "bucket-owner-full-control",
                                    "aws:SourceArn": "$TRAIL_ARN"}}},
    {"Sid": "ConfigAclCheck", "Effect": "Allow",
     "Principal": {"Service": "config.amazonaws.com"},
     "Action": ["s3:GetBucketAcl", "s3:ListBucket"], "Resource": "arn:aws:s3:::$LOG_BUCKET",
     "Condition": {"StringEquals": {"aws:SourceAccount": "$ACCOUNT_ID"}}},
    {"Sid": "ConfigWrite", "Effect": "Allow",
     "Principal": {"Service": "config.amazonaws.com"},
     "Action": "s3:PutObject", "Resource": "arn:aws:s3:::$LOG_BUCKET/AWSLogs/$ACCOUNT_ID/Config/*",
     "Condition": {"StringEquals": {"s3:x-amz-acl": "bucket-owner-full-control",
                                    "aws:SourceAccount": "$ACCOUNT_ID"}}}
  ]
}
EOF
aws s3api put-bucket-policy "${A[@]}" --bucket "$LOG_BUCKET" \
  --policy file://policies/log-bucket-policy.json

# 2. Trail that records ONE region only, without log file validation (weak)
aws cloudtrail create-trail "${A[@]}" --name "$TRAIL" --s3-bucket-name "$LOG_BUCKET" \
  --no-is-multi-region-trail --no-enable-log-file-validation
aws cloudtrail start-logging "${A[@]}" --name "$TRAIL"

# 3. AWS Config is not set up (weak) — nothing to create
# 4. The log bucket has no access logging (weak) — nothing to create

echo "Module 1 build complete."
chmod +x build/m1-build.sh
./build/m1-build.sh
If your account already has a trail that records all regions, the multi-region check passes even before the fix. That is expected: the check looks at the whole account, not only this project's trail.

Step 2: Scan and read the results

source ./env.sh
pscan --service cloudtrail config -o scans/m1-before

Open the HTML report in scans/m1-before. Find these checks:

CheckExpected resultWhy it fails
cloudtrail_multi_region_enabledFAILThe trail only records events in ap-south-1. Activity in any other region, for example an attacker starting servers in another region, is not recorded.
cloudtrail_log_file_validation_enabledFAILWithout validation, nobody can prove that a log file was not changed or deleted after it was written.
cloudtrail_logs_s3_bucket_access_logging_enabledFAILThere is no record of who read or deleted the log files in the bucket.
config_recorder_all_regions_enabledFAILAWS Config is not recording, so there is no history of how resources changed.

Step 3: Fix the weaknesses (after state)

The fix script changes the trail, adds access logging and starts AWS Config.

fix/m1-fix.sh
#!/usr/bin/env bash
# Module 1 fix: logging with strong settings (after state)
set -euo pipefail
cd "$(dirname "$0")/.."
source ./env.sh

# 1. Trail records ALL regions and signs its log files
aws cloudtrail update-trail "${A[@]}" --name "$PROJECT-trail" \
  --is-multi-region-trail --enable-log-file-validation

# 2. Access logging for the log bucket, stored in a separate bucket
aws s3api create-bucket "${A[@]}" --bucket "$ACCESS_LOG_BUCKET" \
  --create-bucket-configuration LocationConstraint="$AWS_REGION"
cat > policies/access-log-bucket-policy.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "S3ServerAccessLogs", "Effect": "Allow",
     "Principal": {"Service": "logging.s3.amazonaws.com"},
     "Action": "s3:PutObject", "Resource": "arn:aws:s3:::$ACCESS_LOG_BUCKET/*",
     "Condition": {"ArnLike": {"aws:SourceArn": "arn:aws:s3:::$LOG_BUCKET"},
                   "StringEquals": {"aws:SourceAccount": "$ACCOUNT_ID"}}}
  ]
}
EOF
aws s3api put-bucket-policy "${A[@]}" --bucket "$ACCESS_LOG_BUCKET" \
  --policy file://policies/access-log-bucket-policy.json
aws s3api put-bucket-logging "${A[@]}" --bucket "$LOG_BUCKET" --bucket-logging-status \
  "{\"LoggingEnabled\": {\"TargetBucket\": \"$ACCESS_LOG_BUCKET\", \"TargetPrefix\": \"log-bucket/\"}}"

# 3. AWS Config records every supported resource type
aws iam create-service-linked-role "${G[@]}" --aws-service-name config.amazonaws.com \
  >/dev/null 2>&1 || echo "AWS Config service-linked role already exists."
aws configservice put-configuration-recorder "${A[@]}" --configuration-recorder \
  "name=default,roleARN=arn:aws:iam::$ACCOUNT_ID:role/aws-service-role/config.amazonaws.com/AWSServiceRoleForConfig" \
  --recording-group allSupported=true,includeGlobalResourceTypes=true
aws configservice put-delivery-channel "${A[@]}" \
  --delivery-channel "name=default,s3BucketName=$LOG_BUCKET"
aws configservice start-configuration-recorder "${A[@]}" --configuration-recorder-name default

echo "Module 1 fix complete."
chmod +x fix/m1-fix.sh
./fix/m1-fix.sh

What changed

CloudTrail trail
- aws cloudtrail create-trail ... --no-is-multi-region-trail --no-enable-log-file-validation+ aws cloudtrail update-trail  ... --is-multi-region-trail    --enable-log-file-validation
Log bucket
  Log bucket access logging- (none)+ LoggingEnabled: TargetBucket = sf-secure-store-access-logs-<suffix>, TargetPrefix = log-bucket/
AWS Config
  AWS Config- no configuration recorder+ configuration recorder "default": allSupported=true, includeGlobalResourceTypes=true+ delivery channel "default": s3BucketName = sf-secure-store-logs-<suffix>
If your account already has a configuration recorder in ap-south-1 with a different name, put-configuration-recorder fails, because only one recorder is allowed per region. In that case, start your existing recorder instead with aws configservice start-configuration-recorder and its name.

# Compare the number of failed findings before and after
grep -c ";FAIL;" scans/m1-before/*.csv scans/m1-after/*.csv
Why scan with -f ap-south-1? The pscan helper limits scans to one region to keep them fast. A full account review should scan every region, because AWS Config and other services are set up per region.

Some new failures may appear, for example the new access log bucket has no access logging of its own. Logging the access log bucket would only move the same problem to another bucket, so it is normal to stop here and protect that bucket with tight permissions instead.

Step 5: Add this module to the clean-up script

Keep these resources: the next modules use the log bucket and AWS Config. Paste this block into cleanup.sh directly below the set +e line.

cleanup.sh — Module 1 block
# --- Module 1: Configuration Monitoring ---
aws configservice stop-configuration-recorder "${A[@]}" --configuration-recorder-name default
aws configservice delete-delivery-channel "${A[@]}" --delivery-channel-name default
aws configservice delete-configuration-recorder "${A[@]}" --configuration-recorder-name default
aws cloudtrail delete-trail "${A[@]}" --name "$PROJECT-trail"
aws s3 rm "s3://$LOG_BUCKET" --recursive "${A[@]}"
aws s3api delete-bucket "${A[@]}" --bucket "$LOG_BUCKET"
aws s3 rm "s3://$ACCESS_LOG_BUCKET" --recursive "${A[@]}"
aws s3api delete-bucket "${A[@]}" --bucket "$ACCESS_LOG_BUCKET"
